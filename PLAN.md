# Glossa Catholica — development plan

A living document: what's done, what's in flight, what's next, and why — organized by phase with dependencies and honest sizing. Distinct from `docs/decisions.md`, which is an **append-only historical log** of decisions as they were made (read it for _why_ something is the way it is, and when it changed). This document is the opposite shape: it gets rewritten as reality changes, has no history of its own, and exists to answer "what should someone work on next, and in what order." When a phase here ships, its "why" belongs in a new `decisions.md` entry, not a rewrite of this file's prose.

Sizing is stated honestly throughout: a measured figure is presented as one (with how it was measured); anything else is explicitly labelled an estimate. Where sizing isn't yet knowable (an item nobody has scoped in detail), that's stated too, rather than guessed at.

## Sequencing and recommendation

Two things actually gate order here; everything else is priority, not sequencing.

- **Latin is no longer gated on anything.** The architecture question below has a recorded decision and built code (`docs/decisions.md`, 2026-08-23). The Bible went first for exactly the reason the old text here gave for waiting: it is the smallest surface on which to debug the new interaction — one work type, a corpus layer already language-agnostic, and no symmetry check in the path. The remaining Latin work is ordinary scraping plus one real design question about `check_language_symmetry`.
- **Search (#2), footnotes-as-sidenotes (#3), and the design pass (#4) are independent of Latin and of each other.** None blocks or is blocked by the rest of this list; they compete for attention on priority, not sequencing. Footnotes-as-sidenotes and the design pass share enough surface area (typography, spacing) that doing them together is likely more efficient than sequencing them, but that's a scheduling convenience, not a dependency.
- **Enrichment (#5, #6) is lowest urgency.** Both need an external, non-vatican.va source that hasn't been evaluated yet, so the first real step for either is a research pass in `docs/research/` style, not implementation.

**Recommended order:**

1. **Search (#2), footnotes-as-sidenotes (#3), design pass (#4)** — run on priority; footnotes-as-sidenotes and the design pass are worth doing together for their shared typography/spacing surface.
2. **Enrichment (#5, #6)** — start with the research pass each needs before implementation is scopeable.
3. **Latin for the CCC and documents** — scoped as a phase below. No longer blocked; competing on priority rather than waiting on a decision.

## Latin — the Bible is done; the CCC and documents are the phase

`docs/research/latin-sources.md` establishes, with live 2026-08-15 fetches, that Latin is fetchable and addressable for the Bible (two independent options — Nova Vulgata on vatican.va with Hebrew Psalm numbering, or the Clementine/Hetzenauer Vulgate from `sacredbible.org` matching the corpus's existing Vulgate numbering), all 16 Vatican II documents, the CCC, and a real (if uneven) slice of encyclicals — notably filling exactly the gap where Portuguese is weakest (Leo XIII: 64% Latin vs. 17% Portuguese, because Latin was the actual promulgation language). The Compendium has no Latin edition anywhere on vatican.va — a permanent gap, not a future scrape target.

**Three of the four preconditions this section used to list are now met.** The architecture question has a decision and code; the Bible edition choice was made and built (Clementine/Hetzenauer over Nova Vulgata, with the reasoning and the disqualification of a third candidate in `docs/research/vulgate-edition-choice.md`); and the Psalm-numbering worry turned out not to apply to the edition chosen, which prints the traditional Vulgate numbering the corpus already assumes.

**What is left, honestly stated:**

- **The two-URL-template reality** (`_lt.html` suffix for the "archive" template families vs. `/la/` path segment for the "content" families, `latin-sources.md` §4) still needs a scraper design. Note this is the same split `vatican_docs.py` already routes for EN/PT, so it is a third `lang` argument rather than a new family — but nobody has written it.
- **`check_language_symmetry` hardcodes two languages** at both ends: `_WORK_ID_RE` only recognises `en`/`pt` as trailing language codes (a Latin work directory would be silently skipped rather than checked), and the comparison is pairwise-for-exactly-two. Generalising the mechanism is mechanical.
- **What that check should _assert_ once Latin is in it is not mechanical, and is still undecided.** It currently treats a section-count mismatch as evidence of a parsing defect, which is reasonable between two independent translations. Latin is the normative text the vernaculars translate, so a Latin/vernacular mismatch may be what translation is rather than a bug — comparing each vernacular _against Latin_ when Latin is present is plausibly the better check than comparing everything pairwise. The Bible offers a precedent worth reading first: there, adding the base text turned an unresolvable "both are faithful" into an adjudicable question (`docs/decisions.md`, 2026-08-23), which argues for the against-Latin shape.
- **The Latin CCC's populated `abbrev_lt.htm`** (`latin-sources.md` §5) remains a second, independent path to the `abbreviations.json` gap in #5 — still not chosen, still not needed.

The Compendium has no Latin edition anywhere on vatican.va and never will; that is a source-level fact to design around, not a scrape target.

## Architecture: UI language vs. content language, once Latin exists

> **Status: decided and built, 2026-08-23.** Option 1 below was chosen and implemented for the Bible; `docs/decisions.md` records what shipped. The analysis is kept as written because the same question returns for the CCC and the document families, where Latin is normative rather than a third translation. The one part still open is the pipeline half — `check_language_symmetry` — discussed at the end.

**The problem, precisely.** `docs/decisions.md`'s "Content language follows UI language" (2026-08-15) made UI language the primary control: switching it switches both chrome and, by default, content edition, with a per-work-type override as the deliberate escape hatch for a reader who wants a specific edition regardless of interface language. That design is sound for a world where content languages and UI languages are the same two-element set (`en`/`pt`) — which is what `site/src/lib/i18n.svelte.ts`'s `UiLang = 'en' | 'pt'` type encodes, and what `content.svelte.ts`'s `ContentStore` was built against.

Latin breaks the premise, not the mechanism: **nobody is asking for a Latin interface, but readers will very much want the Latin text.** So for the population that wants Latin, the override isn't an escape hatch from a sensible default anymore — it's the _only_ path to what they want, since no UI language will ever default to Latin. Concretely, in the code as it stands today:

- `UiLang` (`i18n.svelte.ts`) is a closed two-value union. Latin can never be a `UiLang` value under the current design (correctly — nobody wants Latin chrome) — but that also means `content.langFor(type)`'s fallback (`?? i18n.lang`) and `defaultWorkId(type, lang)`'s matching logic (`corpus.ts`) will never _produce_ Latin as a default for any UI language, which is fine and intended.
- The problem is `content.svelte.ts`'s override lifecycle: `ContentStore#set` stores `{ workId, forUiLang: i18n.lang }`, and `#activeOverride` discards the override the moment `i18n.lang` no longer matches `forUiLang`. This is exactly the right behavior for the case the Aug-15 decision was designed around (a reader who picked the PT Bible under an EN interface probably _does_ want that reset when they deliberately switch interface language — that's the decision's own stated rationale). It is exactly the _wrong_ behavior for a reader who picks the Latin Bible: there is no UI-language event that should ever "naturally" supersede a Latin pick, because Latin was never reachable as anyone's default in the first place. As built today, a Latin override would silently evaporate the next time the reader touches the language switcher for any reason — an unpleasant surprise for exactly the readers this feature exists to serve.
- `listEditions(type)` and `defaultWorkId(type, lang)` (`corpus.ts`) are, encouragingly, already language-agnostic — they sort/filter over `WorkManifest.language` generically and don't hardcode `en`/`pt` anywhere. Adding a Latin `WorkManifest` needs no change here. The friction is entirely in the override's lifecycle and in `UiLang`'s type, not in the corpus access layer.
- `pipeline/scrapers/vatican_docs.py`'s `check_language_symmetry` hardcodes a two-language world at both ends: `_WORK_ID_RE = re.compile(r"^([a-z][a-z-]*)\.(.+)\.(en|pt)$")` only recognizes `en`/`pt` as valid trailing language codes at all (a Latin work directory wouldn't even match the regex, so it would be silently excluded from validation rather than checked), and the pairwise comparison (`"en" not in langs or "pt" not in langs: continue`) is written for exactly two languages, not N.
- `docs/decisions.md`'s "Language symmetry principle" (2026-08-14) describes the mechanism in explicitly binary terms — "the toggle keeps the ID, swaps the language" — language that assumes exactly two co-equal translations. It stops fitting once a third language exists for only some works (Latin exists for the Bible, Vatican II, CCC, many encyclicals — never for the Compendium), and once one of those languages (Latin, for conciliar/papal texts specifically — `latin-sources.md` §3–4) is not a co-equal translation at all but the **normative text the others translate**.

**Options.**

1. **Split `ContentLang` from `UiLang` as a type, and make the override's persistence conditional on whether its language is itself a UI language.** `UiLang` stays `'en' | 'pt'` — the interface never needs more. A separate, open `ContentLang` (or just `string`, since `corpus.ts` already treats language generically) is used wherever an edition's _language_ is discussed, distinct from the interface's language. The one behavioral change needed: `ContentStore`'s reset-on-UI-switch rule should fire only when the override's content language is also a UI language (today's `en`/`pt` case, unchanged) — a pick whose language _isn't_ a UI language (Latin) has no UI event that should ever clear it, so it persists until the reader explicitly changes it. This is a small, precisely scoped change to one function's condition, not a rewrite of the store.
2. **Make every override sticky regardless of language — drop `forUiLang` scoping entirely.** Simpler mental model (one rule: an override persists until changed, full stop), but it re-opens the specific problem the Aug-15 decision solved for the `en`/`pt` case: a reader who picks the PT Bible under an EN interface, then deliberately switches to a PT interface expecting PT content throughout, keeps a Bible edition that's now redundant with the new default rather than resetting to it. Trades away a one-day-old decision's stated benefit ("fewer surprising states") for the `en`/`pt` majority, to simplify handling the Latin minority.
3. **Fully decouple UI language and content language for every work, as two independent, always-explicit controls** — closest to the _original_ (pre-Aug-15) design this project already tried and reversed once. Most conceptually honest given Latin's existence, but solves a problem Latin doesn't actually create for `en`/`pt` readers, and re-opens a decision made specifically to reduce surprising states for the common case.

**Chosen and built: Option 1** (2026-08-23 — see `docs/decisions.md` for what shipped). It's the narrowest change that preserves the Aug-15 decision's benefit for the population it was designed for (`en`/`pt` readers, the overwhelming majority) while making the override genuinely load-bearing for the population Latin actually affects, without re-litigating a one-day-old decision or over-generalizing past what's actually needed. The corpus/data layer already supports it with no changes (`listEditions`/`defaultWorkId` are already generic); the work is confined to `UiLang`'s type declaration and one conditional in `ContentStore`.

**For the pipeline check**, the minimum fix is mechanical — generalize `_WORK_ID_RE` to accept any language code, and generalize the pairwise comparison to run over however many languages are actually present for a given `(family, slug)`, not just `en`/`pt`. The more interesting, undecided question is _what_ the check should assert once Latin is one of the languages compared: `check_language_symmetry` currently treats a section-count mismatch as evidence of a parsing defect, reasonable when comparing two independent translations of the same source. Once Latin (the normative text for conciliar/papal documents) is in the comparison set, a Latin/vernacular mismatch might be a real translation-structure difference rather than a defect — comparing each vernacular _against Latin specifically_, when Latin is present, may be the more principled check than comparing all present languages pairwise against each other. Not resolved here; a genuine design question for whoever builds Latin ingestion, flagged so it isn't rediscovered mid-implementation the way `check_language_symmetry` itself was originally motivated by a real, found defect (`docs/research/vatican-documents.md` §6).

**`docs/decisions.md`'s "toggle" language** should be revisited in a future dated entry once an option above is actually chosen — not rewritten here, since this plan doesn't alter the historical log.
