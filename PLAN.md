# Glossa Catholica — development plan

A living document: what is left, why it matters, what it depends on, and honest sizing — organized so that someone can answer "what should I work on next, and in what order." Distinct from `docs/decisions.md`, which is the **standing statement of the design choices that are not obvious from the code** (read it for _why_ something is the way it is); neither file is a history, and git holds that.

This document gets rewritten as reality changes and has no history of its own. **It does not restate what shipped.** A phase that lands leaves this file entirely — and it earns a line in `decisions.md` only if it left behind a non-obvious rule, not merely because it happened.

Sizing is stated honestly throughout: a measured figure is presented as one (with how it was measured); anything else is explicitly labelled an estimate. Where sizing isn't yet knowable — an item nobody has scoped in detail — that is stated too, rather than guessed at.

## Sequencing and recommendation

Nothing here gates anything else; order is a priority argument, not a dependency one.

- **The row that used to lead this list has been paid off.** #3 led on a claim no other gap could make — that it was work which _revealed_ something rather than adding something, an apparatus that cost a crawl and rendered nowhere. That is no longer true: the Douay-Rheims's notes and arguments are on the page as of 2026-08-25. What remains of #3 is a question about a different surface, and it is small.
- **Nothing else here gates anything, and #5's sigla table gated nothing in the end.** The reverse citation index was long assumed to wait on it; it did not, and shipped without one. When the table finally arrived (2026-08-26, from the French and Latin editions' own front matter) it created no links either, exactly as predicted here: the CCC cites conciliar documents by siglum and encyclicals by spelled-out title, both of which already resolved, and the sigla that remain unresolvable — DS, PL, PG, CSEL, MGH — name works that are not in the corpus at all. What it did buy was the expansion layer, and evidence: the Latin table states outright that `SC` means Sources chrétiennes, which is a thing `refs-grammar.ts` gets wrong for two editions today (see its `DOCUMENT_SIGLA` docblock).
- **#13 is the only row where the corpus is already paid for and unread.** Six editions vatican.va publishes sit in `raw/` as PDFs, fetched and never parsed. It is also the only row that fixes something currently wrong rather than adding something absent: `ar` and `ru` ship as interface languages with no content behind them, which is the failure mode `CLAUDE.md` names in the other direction. **Decided 2026-08-27: the easy picks go first** — Indonesian, Lithuanian and Belarusian, the three that extract as clean UTF-8, then Russian once its CP1251 re-encoding is in, then the CCC's Arabic and Chinese last. The tradeoff that buys is worth naming rather than discovering: an extraction path proven against three clean Latin- and Cyrillic-script PDFs is no evidence at all that it holds for Arabic's bidi controls and presentation forms. Keep the per-edition normalization step separable from the extraction itself, so Arabic extends the reader rather than rewrites it.
- **#14 is decided and goes first**, ahead of everything above it. It is the only row that needs no engineering at all — one dictionary — and it closes the `UI_LANGS`/`ContentLang` gap at the one place where the corpus already holds a whole work the interface cannot dress.
- **#11 is the big one now, and it is a schema problem wearing a scraping costume.** Do not start it by writing a scraper. The four decisions in `docs/research/haydock.md` are the work; the crawl is 22 minutes. Read `docs/research/patristic-citations.md` first: Haydock is a catena of the same Fathers this corpus already cites, and the measurement there — 69% of 734 patristic works cited exactly once — is the clearest statement of why the value in a catena is the attributions rather than the texts.

**Recommended order** (the first two are decided, 2026-08-27; the rest is still a priority argument):

1. **#14 Malagasy chrome** — one dictionary, no engineering, and the corpus already holds the work it dresses.
2. **#13's easy picks** — Indonesian, Lithuanian, Belarusian: the PDF extraction path proved on the three editions that extract clean, with Russian and then the CCC's Arabic and Chinese behind it.
3. **#9's reader-facing disclosure** — what the 2026-08-25 tier left behind, and a decision more than a task. Alongside it, the 101 unread silent-case candidates: reading them is the only way to find another Acts 14, and there is no tool left to write for it.
4. **#12's Summa half** — the cheapest row on this list and the only one that adds no corpus at all: 8,763 references already resolve forward and reverse nowhere. Its Compendium and Bible-notes half is a decision, and belongs with #3's.
5. **#13's remainder** — Russian, then the CCC's Arabic and Chinese, once the extraction path from step 2 exists and the normalization layer has somewhere to grow.
6. **#11 Haydock** — the largest and most interesting addition, once its schema is settled.
7. **#2 search** — the largest unscoped item; needs a prototype before it can be planned.
8. **#1 Latin for the document families** — scoped below.
9. **#5 `related` / #6 Appendix B** — lowest urgency; each still needs a research pass in `docs/research/` style before implementation is scopeable.

## Latin — the document families

The CCC half of this section is done: `ccc.la` landed 2026-08-26 through `ccc.py`'s own edition table, and its abbreviations page along with it. What follows is about the documents.

`docs/research/latin-sources.md` establishes, with live 2026-08-15 fetches, that Latin is fetchable and addressable for all 16 Vatican II documents, the CCC, and a real if uneven slice of encyclicals — notably filling exactly the gap where Portuguese is weakest, because Latin was the actual promulgation language. **The Compendium has no Latin edition anywhere on vatican.va**: a permanent, source-level fact to design around, not a scrape target.

The architecture question this phase used to be blocked on — UI language vs. content language — was decided and built on 2026-08-23; `docs/decisions.md` has the reasoning and the alternatives considered. What remains:

- **The two-URL-template reality** (`_lt.html` suffix for the "archive" template families vs. a `/la/` path segment for the "content" families, `latin-sources.md` §4) needs a scraper design. This is the same split `vatican_docs.py` already routes for EN/PT, so it is a third `lang` argument rather than a new family — but nobody has written it.
- **`check_language_symmetry` hardcodes two languages at both ends.** `_WORK_ID_RE` accepts only `en`/`pt` as trailing language codes, so a Latin work directory would be silently skipped rather than checked, and the comparison is pairwise-for-exactly-two. Generalising the mechanism is mechanical.
- **What that check should _assert_ once Latin is in it is not mechanical, and is undecided.** It currently reads a section-count mismatch as evidence of a parsing defect, which is reasonable between two independent translations. Latin is the text the vernaculars translate, so a Latin/vernacular mismatch may be what translation _is_ rather than a bug. Comparing each vernacular **against Latin when Latin is present**, rather than comparing all present languages pairwise, is the plausible better check. The Bible offers a precedent worth reading first: there, adding the base text turned an unresolvable "both are faithful" into an adjudicable question (`docs/decisions.md` §Oracles), which argues for the against-Latin shape.

  This is flagged here so it is not rediscovered mid-implementation — the way `check_language_symmetry` itself was originally motivated by a real, found defect (`docs/research/vatican-documents.md` §6).
